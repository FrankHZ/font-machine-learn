### NFTR format notes

The game uses Nitro NFTR with reversed section tags:

- Header magic: `RTFN`
- Info: `FNIF`
- Glyph bitmap: `PLGC`
- Width table: `HDWC`
- Char map: `PAMC`

Original `a.NFTR` fields:

- Cell size: `15x15`
- BPP: `2`
- Bytes per glyph: `57`
- Baseline: `15`
- Original glyph count: `1814`

The 2bpp pixels are not normal anti-aliasing. The original font is closer to a hand-tuned bitmap font:

- `0`: transparent/background
- `1`: shadow
- `2`: occasional edge/intermediate color
- `3`: main stroke

Example reference glyph: `0x97B9 = 了`.

### Current preferred NFTR

Latest usable candidate:

- `working/nftr/a-wqysharp13-mixed-leftbottom-v4.nftr`

Preview:

- `working/nftr/a-wqysharp13-mixed-leftbottom-v4-preview.png`

Generation approach:

- Reuse original JP NFTR glyph bitmap + CWDH widths for Latin, numbers, and original punctuation.
- Render new CJK from WQY Zen Hei Sharp 13.
- CJK glyphs are post-aligned to left-bottom in the `15x15` cell.
- Chinese comma `，` is left-bottom aligned.
- Chinese semicolon `；` is left aligned.
- Shadow is generated by adding a 1px down-right shadow.
- Additional shadow patch: if a `0` pixel is surrounded by both `1` and `3` neighbors, convert it to `1`.
- `…` is substituted with original `8164=‥` glyph and width.
- `一二三` are force-reused from original NFTR to avoid bad WQY hinting / vertical placement.

Important script constants in `build_2bpp_nftr.py`:

- `GLYPH_SUBSTITUTIONS = {"…": "‥"}`
- `FORCE_REUSE_CHARS = set("一二三")`
- `VERTICAL_CENTER_CJK = set("一二三")`

Recommended command:

```powershell
python working\nftr\build_2bpp_nftr.py `
  --ttf fonts\wqy-zenhei.ttc `
  --font-index 2 `
  --font-size 13 `
  --render-mode shadow-diagonal `
  --patch-shadow-holes `
  --cell-width 15 `
  --cell-height 15 `
  --baseline 15 `
  --map a.txt `
  --reuse-nftr jp-unpacked\decompressed\a.NFTR `
  --reuse-kind latin-punct `
  --out a-wqysharp13-mixed-leftbottom-v4.nftr
```

Notes:

- `cjk12` was too tight in-game.
- Current natural width uses actual non-empty pixel width as `advance`.
- CrystalTile2 previously set everything to 15, which is bad for spacing.
- The game accepted generated NFTR files structurally.

### Confirmed findings

The old image extraction attempt had multiple issues.

1. NCGR BPP mapping was wrong.

For this game:

- NCGR `depth == 4` means `8bpp / 256 colors`
- NCGR `depth == 3` means `4bpp / 16 colors`

This was verified by forcing 8bpp on a known candidate: the image became recognizable.

Example output:

- `working/image/bpp_compare.png`

2. Many later `ncgpack` records are LZ10-compressed NCGR files.

Compressed entries start with headers like:

- `10 40 C0 00`
- `10 40 93 00`

After LZ10 decompression they become normal `RGCN` files.

`assemble_nitro_images.py` now has:

- `decompress_lz10(data)`

3. Old extracted file indexes are not original table slots.

The `entry_00001...` numbers from old extraction scripts are compressed valid-entry indexes, not original pack table slots. Matching extracted NCGR/NCLR/NSCR by filename index is unreliable.

4. `bgdata.dat` appears to contain 8-byte records:

```text
u16 col0, u16 nclr_index, u16 col2, u16 0xFFFF
```

Examples:

```text
(3, 3, 3, FFFF)
(1400, 20, 920, FFFF)
(2429, 100, 2429, FFFF)
```

Column 1 looks like an NCLR index. Columns 0 and 2 often point into the many NCGR-like records, not necessarily `nscpack`.

5. `ncepack.dat` and `nanpack.dat` contain sprite/cell/animation resources:

- `ncepack`: `RECN` / `KBEC` entries, count `133`
- `nanpack`: `RNAN` / `KNBA` entries, count `133`

A minimal NCER/cell renderer was tested in ad-hoc scripts, but the correct NCGR pairing was not yet found.

### Current status

The script can correctly parse:

- RGCN/NCGR blocks
- RLCN/NCLR palettes
- RCSN/NSCR tilemaps
- LZ10-compressed NCGR records
- 4bpp/8bpp tile pixels
- NSCR tile id / hflip / vflip / palette bank

But complete image reconstruction is not solved yet.

Current problem:

- Some low-index backgrounds become recognizable.
- Most images remain scrambled because the real resource combination/layout is still not fully understood.
- `bgdata.dat` is not a simple `NCGR + NCLR + NSCR` table.
- Many high-index bg records seem to use two NCGR references rather than NSCR.
- Linear scanline rendering was tested and looked worse than tiled rendering, so high-index NCGRs are still tile-based.
- Palette choice also matters, but palette alone does not solve the scrambled layout.
